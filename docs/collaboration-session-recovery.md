# Collaboration session and alert recovery

The incident on 2026-11-01 involved repeated expired-JWT Auth 403s, matching backend permission denials and browser reconnect failures for the same room. A subsequent successful refresh was followed by successful admission. The installed Supabase SDK stops its browser auto-refresh ticker while hidden; the old Yjs provider continued retrying its captured token. Browser visibility was not recorded in the historical diagnostics, so the hidden-tab mechanism is established from the installed SDK and reproduced in regression tests rather than a historical visibility trace.

The collaboration lifecycle now pauses transport while hidden without destroying its Y.Doc, obtains the current SDK session before every new handshake, refreshes near expiry, and reconnects before the active token expires. Token changes update credentials on the same provider/document. Account and room changes still create a separate document. The optional-token transport contract remains available without an authenticated session resolver; a missing authenticated session cannot fall back to that mode, and the server remains responsible for granting access. Late asynchronous resolutions cannot connect an old scope. Server policy rejection stops automatic retry; transient connection/session errors back off and pause after five consecutive failed attempts. A foreground or online transition rechecks the SDK session after transport retry exhaustion; policy rejection and cloud-conflict suspension remain stopped. Explicit retry remains available. Ordinary offline edits retain the prior verified editor boundary, while denial clears it and blocks further edits.

The backend retains diagnostic events and uses a server-only SECURITY INVOKER RPC to atomically claim notification delivery. A fixed 99-key table suppresses the same operation/code for ten minutes across instances and releases, rejects replay of the last request ID, and permits at most six distinct claims in a rolling minute. The existing three-second bounded delivery and Vercel waitUntil lifecycle remain. A claim is consumed before notification delivery: this is bounded best-effort admission, not guaranteed delivery or a retry queue. Claim/storage failure suppresses notification without rejecting an already persisted telemetry batch.

Apply the additive `telemetry_alert_claims` migration before deploying a backend that calls the claim RPC. Old backends remain compatible with the new table/function. Rollback restores the previous frontend/backend deployments; the additive private schema may remain. No customer data, existing policies, service secrets, or SDK package contents change.

Regression coverage includes hidden/visible transitions, refresh near expiry, stale token rejection, account switches, policy rejection, retry limits, actual WebSocket synchronization with retained offline edits across token rotation, database role isolation, real PostgreSQL concurrent single admission, replay, cooldown, and global rate budget. Production verification is recorded separately in the release receipt.

The full browser gate also checks the existing optional-token local protocol contract, the delayed empty-to-advanced canvas transition, and storage startup budgets. Storage UI modules remain in their startup group rather than pulling in the canvas bundle; the advanced canvas shell keeps its lazy module boundary. No budget thresholds or backend authorization checks were relaxed.
