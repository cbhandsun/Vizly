# 普通入口的端口、避障与布局回退修复

日期：2026-09-06。路由版本：18。适用复现：企业架构图普通首次打开、页面恢复，以及“标准流程 → 泳道 · 域左右并列（域内上→下）”。

阅读范围：本文前半部分（到“修改范围与回滚”为止）保留较早的普通首开修复轮次，其“最终代码”、49 组 CI 和耗时均指当时版本。随后是修复前架构审计和本次统一实现；当前交付状态以文末为准，不能把历史轮次的完成声明套用于后续修改。

## 问题本质

端口、路径和质量检查原本在不同阶段作决定：恢复数据没有 computedPath 和多数自动 handle，兜底路径按推断方向生成，却没有同步对应 handle；浏览器可能仍用默认上端口。后续绕障候选又按 8px 物理 padding 生成约 9px 的通道，最终提交要求 48px 商业净距。结果是前面的阶段不断产生后面的阶段必然拒绝的候选。

因此，端口错误和布局回退不是两个完全独立的小问题。切换事务保留旧画布的机制在正常工作，真正失败的是事务内部无法及时构造符合最终约束的路线。不能靠取消回退、放松质量门禁或延长超时解决。

## 修复

1. 将端口侧与向外通道作为一次初始决策，按端口约束枚举候选，同时评价障碍物、48px 净距、弯折与长度。优先选择不超过三个弯折的可用通道；仅在无可用通道时补充四弯折绕行，覆盖固定端口受阻的情况。
2. 无既有路线的输入进入一次完整路由事务，避免先执行一次交互修复，再从坏种子重复整套修复。普通首次打开还有另一种输入：Dagre 临时路线已经带 computedPath 和运行时端口锁，但企业图 15/36 条连线受阻，共有 21 次节点命中。受阻边数虽然不到半数，却超过既有交互候选处理额度 12。初始化判定复用这项现有额度：明确标记为临时 Dagre 路线、且问题超过修复额度或占据小图多数时，重建初始路线。局部受损路线和其他引擎的路线保留原有拓扑，继续候选验证及增量修复。手工固定路线不参与重建。
3. 兜底路径同步写入匹配的 sourceHandle/targetHandle，保留同侧自定义 ID，并尊重手工、固定和禁止端口约束。
4. 障碍绕行候选与最终净距检查统一使用商业目标。物理碰撞 padding 保留为检测参数。
5. Worker 内的候选初始化不改写原请求身份、业务边或手工约束；最终结果仍须通过完整质量报告和原子提交。缓存版本升至 18，重新生成 4 份预编译路线。
6. 允许合法交叉后，安全检查的快速返回仍须完成邻近目标端口的合流整理。否则“几何安全”会被误当作“端口整理完成”。该整理沿用原有候选和质量门禁，保留源端位置。

初始化为有界候选构造，不是新的无限搜索器：最多 96 个节点，边数与节点数乘积不超过 5000。缺失、非法、过大或尚未测量的几何交回既有测量与路由流程。这些上限限制计算量，不会授权提交不合格路线。没有添加企业图或具体节点 ID 的生产分支，没有提高超时、baseline 或搜索预算。

行业方案采用相同的职责划分：在固定节点几何上考虑端口候选、通道和路径代价，再确定路线坐标。yFiles 的 EdgeRouter 文档说明了空间划分、路径搜索、坐标确定三个阶段，以及端口候选约束。[yFiles 官方文档](https://docs.yworks.com/yfiles-html/api/EdgeRouter/)

48px 是 Vizly 的产品净距目标，不是全行业统一值。合法线线交叉仍可保留并用桥接表达，不能为追求零普通交叉制造长距离绕行；端口失配、穿节点和无法解释的重叠继续阻断提交。相关准则已融合到 [连线目标](edge-routing-goals.md)。

- `edgePathQualityGeometry.ts:64` 的可读性成本与最终 polish 的软成本保持相同排序（后者为两倍尺度），不能将这种比例差异认定为目标冲突。

当前共享的是路由规则和评价证据。布局仍先给出节点位置，路由随后在固定几何上寻找路径；上一轮发现的 flow 行列关系被后处理覆盖，正说明布局约束还没有贯穿所有阶段。统一建模的下一步应明确每个阶段必须保留的约束及其版本，而非仅继续提取通用函数。

### 真实的整组协同与未接入能力

生产 Worker 的端点闭合及最终商业净距阶段确实调用 `baseReactFlowDisplayEndpointTrunkClearance.ts`：按已经审计的 source／target 真主干同时移动成员，并通过 `createAtomicRouteTransactionEvaluation` 检查整图硬质量、障碍、锚点和既有主干。`baseReactFlowDisplayDualTrunkJunctionRepair.ts` 也会联动共享目标通道，保留双端角色；`baseReactFlowDisplayOuterPortTransaction.ts` 存在两条边端口组合与外侧通道的整体候选。

边界同样明确：

- `baseReactFlowDisplayRoutingCorridorReservations.ts` 将双角色关联组组成原子预留单元；但 `baseReactFlowDisplayRoutingTopologyPlan.ts:81` 向后投影的是每边 preferred axes。预留成功并不表示所有成员最终同时占用该方案。受限大图路径还会停用这项投影。
- `edgeRoutingWaypointRefinement.ts:626` 继续按边顺序选择路径；`baseReactFlowDisplayInitialRoute.ts:99` 的初始端口／通道选择也是逐边进行。已有的组事务负责特定冲突，未形成所有路径决策共用的组求解入口。
- 交叉簇 beam 有生产调用：深度 4、宽度 8、最多 192 次精确评价。总边数大于 24 时，取第一个严格交叉所属的交叉连通分量；分量不超过 24 才运行 beam，其余边仍参与质量／碰撞检查。超过该范围还有受限 maze 候选，不应描述为完全没有协同修复。它也不构成全组最优证明。
- `repairBoundedHubPortRoleTransaction`（`baseReactFlowDisplayHubPortRoleTransaction.ts:457`）只有定义和测试引用，本次全源码引用检查未发现生产调用。该模块不能计入已接入的组端口求解能力；是否接入仍需按生产预算和收益评估。

应沿着“受影响组共享端口、通道容量和主干约束 → 有界联合候选 → 全图验收”演进，保留现有成熟组事务与预算，不以增加无界搜索来替代建模。

### 原子提交已成立，验收对象仍有缺口

有边布局的调用链为：`useLayoutRoutingTransaction` → `stageBaseReactFlowLayoutRouting` → Worker 精确路径报告 → `DisplayRoutingWorkerCommitReceipt` → 客户端校验及路由补丁重放 → 当前任务中的快照和节点／边／选择提交。收据绑定原始输入身份、输入几何摘要、输出路径摘要及报告摘要。渲染权限再次核对这些身份，使单条边渲染器不能自行替换已授权路径。

**本轮已复现的验收缺口：**

1. 真实 `useLayoutRoutingTransaction` Hook 输入无边图，两个叶节点完全重叠，且通过真实 `parentId` 挂在容器外；仍执行节点提交、一次布局选择提交、一次撤销快照，最后恢复 stable。原因是 `useLayoutRoutingTransaction.ts:112` 只有存在边时才 staging，空边分支的快照提交默认成功。
2. 一条正常连线外加两个远处重叠的孤立节点，使用合法 `candidateSource:'document'`、正式节点投影和真实 Worker 计算，返回 `hardClean:true` 且签发收据。真实父子关系下的容器越界样例也通过精确路径报告。
3. `RoutingHardReport` 没有节点互叠、容器包含或泳道模式／对齐字段。泳道不齐的报告探针只证明这类约束不在报告输入与指标内，不作为错误泳道已在真实页面提交的证据。

因此，当前收据准确含义是“这批连线路径通过约束并对应这份输入几何”，不能扩展为“这份布局整体有效”。原子发布只能保证发布的是同一份结果，不能补足验收中没有定义的规则。

`auditRenderedEdgeRouting` 与四层商业质量聚合器也没有进入每次布局提交的生产调用链。渲染权限保证路径身份，不等于对最终桥接、marker、标签、交互命中区和多尺度体验的像素验收。可在提交前验证最终渲染计划的结构，实际 SVG 与多尺度结果继续由浏览器／导出矩阵校验，避免每次交互都执行昂贵 DOM 全扫描。
