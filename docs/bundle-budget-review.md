# Bundle 预算评估（2026-09-04）

状态：评估建议，尚未调整生产门禁。当前净距修复的旧总量门禁仍为失败，不将预算评估记作修复验证通过。

## 实测与口径

- 当前构建：233 个 JS、41 个 CSS；全部 JS raw 为 9500.02 KiB。脚本显示为 KB，实际除数为 1024。
- 入口静态 JS：9 个文件，约 512.24 KiB raw / 163.42 KiB gzip。约占 JS 总量 5.4%；其余文件不能据此全部称为“非首屏”，因为页面还会动态加载路由和编辑器。
- 单个 ELK Worker 约 1405.88 KiB raw / 428.16 KiB gzip；显示路由 Worker 约 498 KiB raw。总量包含 Worker、不同页面以及导出、3D 等功能资源，不能等同于一次访问的传输量或执行量。
- 现有独立硬门禁包括入口 650 KiB raw / 220 KiB gzip、单 JS 1500 KiB raw / 475 KiB gzip、CSS、唯一显示路由 Worker，以及桌面/移动路由的关键资源数、解码体积、就绪时间。应继续保留。
- 9500.02 对 9500 的超额约 20 字节。它没有可证明的体验影响。上一轮 Bundle 实验仅减少约 0.84 KiB，却需要多轮构建/回归；投入不划算。

## 建议的预算政策

1. 总 JS 硬上限建议为 10000 KiB，约比当前多 5.3% 余量。这是项目工程取舍，不是行业通用性能标准；不自动随版本递增。
2. 9750 KiB 开始预警，要求在后续新增大型依赖之前审查资源归属和加载边界。9500 KiB 保留为本次评估参考值，不再用于拦截几十字节的波动。
3. 原有入口、单块、CSS、路由资源、就绪时间和路由/交互性能门禁保持原值。总量余量不能用于抵消首屏或运行时退化。
4. 首屏提前加载大型可选依赖、重复打入布局引擎、单次依赖变更明显增加实际加载量，应立即调查；一般总量增长集中在依赖升级或功能批次评审。避免每次构建都为几个字节优化。
5. 只有实现前后能证明加载量、解析/执行时间或交互指标改善的优化，才优先于功能修复。静态 gzip 是统一比较口径，不声称部署服务已启用 gzip/Brotli。
